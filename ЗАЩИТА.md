## Как показать работу (30 секунд)

1. «Старт» → «Задача»: пакет проходит `Коммутатор → Брандмауэр → Сервер приложений → База данных`, результат возвращается клиенту, пользователь радуется.
2. «Вероятность ошибки данных» = 0,3: красный треугольник летит клиенту, клиент «исправляет ошибку», задача уходит заново с попыткой 2.
3. «Вероятность отказа БД» = 0,2: база краснеет, администратор подключается по SSH, едет зелёная команда ремонта, обработка продолжается.
4. «Скрыть журнал» — сцена занимает всё окно.
5. «Сброс» — модель возвращается в исходное состояние.

## Вероятные вопросы

**— Почему `Evaluate` виртуальный, если базовый класс «без виртуальных методов»?**

> В C# `override` возможен только для `virtual`-метода — это особенность языка, а не архитектуры. Абстрактных методов в базовом классе нет, сам класс не абстрактный: экземпляр `ProcessingNode` создаётся и работает коммутатором. В C++ было бы то же самое: `virtual` в базе, `override` в наследнике.

**— Что такое делегат?**

> Тип, который описывает сигнатуру метода. Переменная делегата хранит ссылку на метод (аналог указателя на функцию в C++). Событие — это список делегатов: `event NodeCompletedHandler ProcessingCompleted` хранит подписчиков.

**— Зачем явные `add` / `remove`?**

> Это полная форма объявления события. Вместо автоматического поля мы сами решаем, что делать при подписке и отписке: здесь просто добавляем/убираем делегат в хранилище `_processingCompleted`. Заодно видно, что это не «событие по умолчанию».

**— Как объекты связаны между собой?**

> Узел не знает, кто на него подписан: он вызывает `_processingCompleted?.Invoke(...)`. Сегмент в `SubscribeToNode` подписался и в обработчике решает, отправить пакет следующему узлу или вернуть ошибку клиенту. Логика модели не зависит от формы.

**— Чем C# отличается от C++ в этой работе?**

> Концепции те же: инкапсуляция, наследование, полиморфизм, события. Отличия синтаксиса: свойства вместо пары геттер/сеттер, `event`/`delegate` вместо указателей на функции, управление памятью сборщиком мусора.

**— Где создаются экземпляры базового и дочерних классов?**

> `SimulationWorld.cs:100–107`: `new ProcessingNode("Коммутатор", ...)` — базовый, затем `new FirewallNode`, `new AppServerNode`, `new DatabaseNode`.

**— Где второе дерево наследования?**

> `NetworkSegment` → `ClientSegment` / `ServerSegment`. Наследники переопределяют `ResolveDestination` (кому адресовать пакет) и `Draw` (внешний вид сегмента).

## Карта классов (если спросят «а это что за класс?»)

| Класс | Роль |
|---|---|
| `ProcessingNode` | Базовый узел: очередь, обработка, сбой, ремонт, два события |
| `FirewallNode` / `AppServerNode` / `DatabaseNode` | Наследники: своя вероятность сбоя и своя пиктограмма |
| `NetworkSegment` | Базовый сегмент: дорожки, маршрутизация, передача пакетов соседу |
| `ClientSegment` / `ServerSegment` | Наследники: решают, кому адресован пакет |
| `Packet` | Пакет: тип, номер попытки, движение по маршруту, событие `Arrived` |
| `Client` | Отправляет задачи, исправляет ошибки, принимает результат |
| `Administrator` | Получает уведомление об отказе, «чинит» узел командой `Fix` |
| `EndUser` | Стоит рядом с клиентом, радуется результату |
| `SimulationClock` | Единственный источник времени, событие `Tick` |
| `SimulationLogger` | Наблюдатель: пишет события объектов в журнал |
| `SimulationWorld` | Собирает и связывает все объекты, хранит счётчики |
| `MainForm` / `SimulationCanvas` | Интерфейс: настройки, сцена, журнал |
